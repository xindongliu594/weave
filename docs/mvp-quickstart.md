## 打开或启动

当前这台电脑的工作台已运行在 [http://127.0.0.1:4310/](http://127.0.0.1:4310/)，使用原本机数据与设备授权。服务运行时直接打开页面；不要再双击启动器，也不要同时启动两份服务。

当前源码目录为 `C:\Users\JJ\.codex\worktrees\f57c\agent_department`，已安装依赖，实测 Node.js 24.15.0。服务停止后，在此目录打开 PowerShell，沿用原数据启动：

```powershell
node scripts/local.mjs '--data-dir=C:\Users\JJ\Desktop\la\agent_department\.data\local'
```

保留这个终端；Ctrl+C 停止服务，再运行同一命令重启。`--data-dir` 指向完整本机数据目录，现有数据库、凭据、工作区和设备授权继续保留。无需复制密钥或重新授权。启动锁会拒绝访问同一目录的第二个服务。

在另一台电脑首次安装时，需要 Node.js `^22.19.0 || >=24`，在源码目录执行：

```powershell
npm ci
npm --prefix services/agent-runtime ci
npm run local
```

双击 `start-local.cmd` 或运行 `npm run local` 默认使用**这份源码目录下**的 `.data/local`，是独立环境，不会自动读到上述原配置。启动器也可接受参数，例如 `start-local.cmd "--data-dir=C:\Users\JJ\Desktop\la\agent_department\.data\local"`。网页端口占用且需要另一个独立环境时，可加 `--web-port=4312`；同一数据目录仍不能双开。

## 从需求到交付

1. **检查模型。** 新环境进入“模型目录”，填写中转站完整 API 前缀、Key、模型和单价，再分别测试连接与工具能力。已有环境可直接沿用已通过测试的模型。模型测试、需求对话及执行均按中转站计费；保存配置不自动调用模型。
2. **持续讨论。** 首页描述需求，回答追问，继续补充或修改人员与任务。页面分别显示“尚未生成团队方案”“本轮方案未生成成功”和待确认团队方案。失败或有未发送修改时，先继续生成有效新草案；“继续获取回复”用于取回结果不明的原请求。
3. **确认组队。** 检查完整任务草案，点击“确认组建团队”。只有此时保存部门、员工和项目。后续调整须重新生成方案并点击“确认更新团队”，运行前再检查项目。
4. **检查并批准。** 项目中检查模型、工具、依赖、输入来源、输出文件、验收标准与预算。验证命令填写精确可执行命令，例如 `node --test todo.test.mjs`；允许写入范围逐行填写实际相对路径，不能把说明文字或模糊目录范围当作文件授权。完成校验后批准运行。
5. **逐次审批。** 执行页显示当前节点、员工状态、累计费用及“任务、交付物与审批”。阅读命令和参数后点击“批准这次操作”；拒绝或停用后不会直接执行。文件、代码和报告由员工生成，用户不需要替员工补写交付。
6. **验收与下载。** 查看各节点完成记录、独立审查结论及“本机操作回执”的真实退出码和输出。交付物可预览和下载；“导出完整追溯”保留 Run ID、调用与审批记录。按员工生成的 README 启动和测试项目。命令通过但任务交接或经理验收未完成时，项目仍未完成。

## Todo API 示例

首页可输入：

> 请组建经理、开发、独立 QA 共 3 名员工，按 4 个串行任务完成仅用 Node 内置模块的 Todo API：开发生成 server.mjs、todo.test.mjs、README.md；QA 生成 acceptance.test.mjs，启动真实 CLI 子进程并通过 HTTP 独立验证；QA 再审查开发与独立测试，输出文件留空；最后经理完成文字验收。服务只绑定 127.0.0.1，提供 Todo 增删改查及 400/404；README 写明 Windows 启动与测试命令。所有文件由员工生成，命令逐次审批。

确认后在“编辑方案”核对以下合同，必要时在网页修正后保存新版本：

| 节点 | 合同检查 |
| --- | --- |
| 开发 implementation | 输出及写入范围为 `server.mjs`、`todo.test.mjs`、`README.md`；验证 `node --test todo.test.mjs`。 |
| QA verification | 依赖开发；输入三个开发文件，生产任务均指向开发；输出与写入范围仅 `acceptance.test.mjs`；验证 `node --test acceptance.test.mjs`，须实际启动服务并请求 HTTP。 |
| QA review | 依赖开发与 verification；被审查任务指向开发；输入三个开发文件及 `acceptance.test.mjs`，各自生产任务分别指向开发与 verification；输出文件留空，沿用只读独立审查。 |
| 经理文字验收 | 依赖 QA review；核查真实测试回执、交付文件和运行说明，完成文字结论。 |

本轮采用预算 **$0.48**、最多 **3** 人、并发 **1**、模型调用 **80** 次、每员工每任务 **35** 次、时限 **1800** 秒、上下文 **192000** 字节。已用费用与调用次数在恢复时继续累计；沿用既有全局/部门限制，不因失败自动扩大额度。工具只授予任务需要的读取、写入与测试能力。

## 中断后恢复

服务重启后先打开原运行，查看停止原因、已完成节点、审批、操作回执与费用状态。已完成的可信节点保留，未完成节点续跑，旧命令审批不会重用。点击“恢复未完成任务”会创建新 Run；“完整重试”会重新执行全部任务。

如提示费用待核对，进入“系统设置 → 每日预算与待核对费用”，找到对应 Run 的“核对这次费用”。依据中转站账单填写完整输入/输出 Token、请求编号或查询时间等核对依据，勾选已核对账单，再点击“确认记录用量”。只有供应方确认没有扣费，才能把两项都填 0；没有账单就保持受阻。之后回原运行刷新，再按原额度恢复。

若出现结果未知的文件修改或命令，先检查操作详情与现有文件，确认实际影响后才勾选核对确认。系统不会盲目重放。档案损坏、版本变化、知识授权失效或额度耗尽的具体原因会阻止恢复，应先处理页面提示。
