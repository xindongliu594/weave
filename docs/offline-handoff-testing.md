## 本次实际验证

新增订单汇总固定资料、三个使用同一模型名的独立员工、五个预先批准的任务，以及缺失文件/上游失败诊断。执行 `npm run test:handoff` 可复验，无模型 API 调用。

检查用固定代码实际计算：错误模块得到 1798 分，正确值为 4095 分。检查员工据此输出诊断，同一开发员工恢复原会话执行已批准的修复任务，原检查员工恢复后复验。固定预期值没有送给开发员工以伪造计算结果。

真实执行的部分是 DSH Host、AgentTeams 调度/消息、产品文件工具注册和员工授权、会话持久化、追溯，以及固定程序的 Node 执行。模型回复和文件执行器为测试替身；没有运行生产 API/数据库/审批 UI、Docker 沙箱或真实模型。

### 发现并修复：空闲员工接续任务

原 Host 只加载 session persistence，没有加载 `@deepseek-ai/dsh-session-query`。员工结束一轮后，continuable Agent 的活跃实例可以被释放；下一项任务需要通过公开查询服务恢复已保存的会话。原场景在第 4 项 repair 停留 pending，交付尝试反复增长。

在 persistence 之后挂载已锁定依赖中的公开 session-query 服务后，五项任务完成；producer 和 checker 分别沿用自己的 session ID，保留先前会话，各任务只分派一次。没有修改第三方包、依赖版本或团队调度器。

### 第一轮未修复：任务完成与文件就绪没有绑定

missing-file 场景让上游不写 `lib/money.mjs`，但提交 `completed`。当前调度仍启动 application，后者通过真实产品 filesystem 工具入口读文件时才得到缺失错误，并按脚本报告失败。任务依赖只知道上游状态，不会解析其自由文本输出并验证文件。

这一诊断测试的绿色表示“成功复现当前缺口”，不表示系统已经具备文件启动门禁。运行摘要始终单独输出 GAP，后续实现门禁后应把此诊断改为正向回归测试。

## 文件依赖和任务依赖如何落地

依赖首先绑定任务和交付物，再通过任务负责人关联员工。同一员工可以有多个互相独立或前后依赖的任务；换人不应破坏任务依赖。

| 依赖类型 | 例子 | 获取方式 | 执行侧检查 |
|---|---|---|---|
| 代码/构建依赖 | report.mjs 导入 lib/money.mjs | 导入分析、构建清单、测试、实际读取记录 | 路径存在，版本正确，构建与测试通过 |
| 数据/文档依赖 | 报告需要订单表和统计口径 | 用户输入、模板、规划模型的显式声明 | 来源、版本、数据结构、所需字段与授权 |
| 任务前置依赖 | 复验必须等待修复 | 任务图声明 | 前置状态、输出验收与版本绑定 |
| 共享资源冲突 | 两人同时修改同一文件或操作同一浏览器 | 写入范围声明、运行中资源申请 | 顺序、锁或版本条件写，冲突不静默覆盖 |

文件名和自然语言不能完整推断真实依赖。静态 import 能发现一部分代码关系，动态路径、外部数据、配置、业务语义依赖仍可能需要模型推断和用户补充。

建议下一阶段增加产品级输入/输出契约（以下为设计，不是当前字段）：

- 任务输入绑定 `artifactId`、产出任务 ID、路径、已批准版本或 SHA256、必需的验收记录。
- 任务输出记录产出任务/attempt、版本、SHA256、实际读取的输入版本与验收证据。
- 调度器核对“前置已完成＋输入存在＋版本匹配＋必要验收通过＋员工有权限”后才执行。
- 缺失输入进入等待/阻塞状态，标明需要哪个产物；来源未知或超出批准范围时询问用户。
- 上游文件变更后，根据记录的实际输入关系标记受影响结果过期，再安排必要的重算/复验；已运行的任务仍固定其原输入版本。
- 重试、修复与复验使用新的 attempt/任务版本展开流程，避免把原任务图改成依赖环。版本条件写解决覆盖冲突，不能单独替代下游结果失效判断。

## 人工介入与自进化的边界

前期采用固定模板或手工声明输入、输出和依赖，人工确认整体计划；确定规则由程序执行。接入真实模型后，可以让经理模型提出依赖，程序检查环、缺失来源、权限、版本和冲突，范围内按批准策略运行。运行中发现未知依赖，形成变更建议，仅对需要新增输入、扩大范围或有歧义的部分请求确认。

自进化可以从多次任务中提炼更准确的拆分模板、检查规则和技能，经评测后发布。依赖等待、文件存在性、版本一致性与授权始终由基础运行层执行，不能让学到的经验绕过硬检查。
