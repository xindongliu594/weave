# RAG：API 与本地组件分工方案

用户澄清的约束：整个软件部署JJ；大型语言模型推理用已有API，轻量检索、嵌入和重排组件仍可按实测代价在JJ运行。此前清理的是隔离试验缓存，生产软件和原数据保留。本方案是下一阶段设计，尚未实现云端证据充分性验收或生产接入。

## 复用什么

- 保留现有授权过滤、固定版本知识库、轻量关键词召回与knowledge_read，不复制第二套知识平台。
- 本地分词、索引、小型嵌入或重排按质量与资源实测选用；云API作为需要大语言模型理解/证据判断的环节，不强制替代每一次本地排序。之前FlashRank候选也有精度问题，不能仅因本地组件获允许就直接部署。
- 使用网页已配置的 Go · DeepSeek V4.1 Flash；目前配置状态available、模型名deepseek-v4.1-flash、关闭thinking，登记费率输入$0.30/百万、输出$1.20/百万。这是配置快照，不是本轮真实账单或实时可调用证明。Key只留已有加密存储。
- API传输复用 apps/api/src/provider.ts；付费调用复用cost-control.ts的completeBudgeted，保留预留、回执、超时和未知费用规则，不直接绕账本发送fetch。
- 评测可借鉴 [Ragas Context Precision](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_precision/) 的相关片段判断；[Promptfoo兼容API](https://www.promptfoo.dev/docs/providers/openai/) 可作为独立回归驱动。只核对了官方能力，尚未安装/验收；不得通过这些驱动绕过为伍预算或把其默认评判模型算作用户已授权。

## 产品流程

**检索子问题 → JJ按员工授权/固定版本召回与排序 → 必要时API大模型判断证据 → JJ核验引用 → 员工按范围复用 → QA核验实际结果。**

模型输出结构化的full/partial/none、所选片段引用、覆盖的子问题、仍缺什么和简短依据。partial可复用已支持部分，缺失部分按新工作流程处理，不能将“未能回答整个开发任务”误作“已有测试方法完全无用”。只有full才能用于声称资料完整支持该次知识结论。

程序核对选中引用确实属于这名员工的批准版本集合，保持完整正文/hash；模型不能扩大可见知识范围。先限制候选数量，再在上下文容量和预算内读取；过长按固定片段分批，不静默截断后声称没有证据。JJ运行整个软件、Agent调度、沙箱与实际代码测试；大语言模型推理在API侧完成，轻量本地模型仍可用于检索/排序。

## 按顺序推进

1. 用现有两份授权方法及合成的无答案、部分支持、长文尾部、越权/新版案例，固定full/partial/none人工预期；纠正同意图划分，旧查询仅作为回归。先验证现有召回与API证据判断，是否补充本地小模型由实际质量和资源结果决定。
2. 准备一小批真实API调用，限定输入/输出、调用次数和新增费用；先核对原累计/阶段/项目规则是否容纳该验收。额度不足按现有审批处理，不增加总授权，不挪用旧未知预留。
3. 在现有预算调用入口评测结构化判断、引用真实性、错误接受、误拒绝、Token、费用与延迟。模型也可能判断错误，不能只看其confidence或让同一个模型自己给自己判成功。
4. 通过后增加薄的知识选用适配及可见原因；优先合并到员工已有推理步骤，只有需要独立判断时才另开调用。之后验证员工真实复用、QA引用检查和服务恢复时保持同一模型/提示/资料策略。

预算与安全边界继续由程序确定：审批、授权、不可变版本、去重、费用、外部操作是否可重放和真实测试执行，不交给模型自行改变。API可以给建议，实际授权与数据操作仍由Harness执行。
