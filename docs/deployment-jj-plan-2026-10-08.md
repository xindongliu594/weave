# 为伍部署到 jj：准备工作与验证顺序

日期：2026-10-08（北京时间）。本文件是部署计划，本轮没有安装软件、上传项目、迁移数据、改变权限或创建服务。用户指定的 SSH 和设备核对已完成，详见 [设备评估](validation/jj-device-assessment-2026-10-08.md)。

## 已具备的条件

- `ssh jj` 可沿用现有身份与已知主机验证连接。
- Ubuntu 26.04 x86_64；i7-9750H，6 核 12 线程，约 16GB 内存，NVMe 剩余约 433GB。
- Git 与 Python 已可用；现有检查没有发现可用的 Node/npm、Docker/Podman、tmux。
- 当前 Linux 内核启用 Landlock、seccomp 和 cgroup v2，但还没有经过容器或 OpenShell 实际预检。
- Docker 官方当前安装文档列 Ubuntu 26.04 为支持版本。这不代替我们在该机器上的组合验收。[Docker Ubuntu 安装说明](https://docs.docker.com/engine/install/ubuntu/)

## 阶段一：先部署已有为伍 MVP

1. **确认安装和网络条件。** 核对 sudo 安装权限，检查 GitHub、npm、中转站 HTTPS 及所选软件源的可达性。连接/下载检查不调用推理，不使用未知结果的重复请求。
2. **准备服务身份与目录。** 使用独立服务账户和项目、数据、工作区、备份、日志目录；明确目录归属与权限。保留设备现有服务和用户配置，避开已占端口。
3. **安装固定运行环境。** 选 Node 24 和 npm，记录版本与校验来源，沿用项目两套锁文件。OpenRig 也明确支持 Node 22/24，优先统一到已有项目验证过的 Node 24 路线。[项目 engines](../package.json)、[Node 发布状态](https://nodejs.org/en/about/previous-releases)
4. **部署固定源码。** 使用 `codex/weiwu-mvp-validation` 的已推送提交 `4f19ab005f80eb07fd3623e7f2e8792ed5ba71ac` 作为第一轮基线，保存提交 SHA；原开发目录和原业务数据继续保留。以后升级使用独立 release 目录和回滚入口。
5. **先做零模型费用验证。** 安装根项目和员工运行器依赖，运行类型检查、生产构建与相关本地回归；用独立数据目录进行启动、关闭和重启验证。当前 PGlite 本机方案先沿用，另行引入外部 PostgreSQL不属于第一次启动前提。
6. **建立网页访问。** 当前启动器/API 默认绑定 `127.0.0.1`。第一轮沿用 SSH 隧道访问，Windows 浏览器连接本机转发端口；没有公网开放要求。需要长期远程入口时另配认证代理、HTTPS 和来源校验。
7. **配置 API 与迁移边界。** 在新环境网页保存中转站信息，优先读取模型目录和已存在能力证据。新库不代表新增预算授权；真实请求前核对原已批准额度、历史未知预留与唯一活动环境。旧数据库、知识、交付和凭据迁移走备份恢复并逐项验证，Windows 本机路径授权要重新映射和核对。
8. **验证真实主流程。** 经预算准入后验证需求对话、确认组队、员工执行、独立 QA、经理验收和停止恢复。软件安装完成、HTTP200 或固定测试响应都不能代替真实项目通过。

第一轮 Linux 手动启动的预期命令为：

```sh
npm ci
npm --prefix services/agent-runtime ci
npm run build
node scripts/local.mjs --production --data-dir=/srv/weiwu/data/pilot
```

上述 `/srv/weiwu` 是计划目录，不表示已经创建；账户、目录权限及启动检查成功后才能使用。人工检查完成后再配置 systemd 服务，固定 Node 可执行路径、工作目录和数据路径，处理重启、日志与正常停止。不能让服务自启自动重放费用或结果不明操作。

第一轮 Windows 访问命令示例：

```powershell
ssh -N -L 127.0.0.1:4312:127.0.0.1:4310 jj
```

服务运行后浏览器访问 `http://127.0.0.1:4312/`；实际实施前再检查两端端口可用性。

## 阶段二：接 OpenShell 执行隔离

- 按 Docker 官方仓库和选定版本安装 Docker Engine、Buildx、Compose 插件，记录其系统服务与网络变更。容器权限交给可信管理侧；员工工作负载不获得宿主 Docker socket。[Docker 安装文档](https://docs.docker.com/engine/install/ubuntu/)
- 选固定 OpenShell 发布与镜像版本，核对 SDK、Linux 内核和驱动的实际匹配条件；不把 main 开发能力当稳定包能力。[OpenShell 支持矩阵](https://docs.nvidia.com/openshell/dev/about/support-matrix)
- 独立目录验证文件越界、网络拒绝、命令取消、产物哈希往返及沙箱重启。先保留为伍已有审批、预算和恢复账本，隔离层承接工具执行。
- 用少量并发起步，实际计量 CPU、内存和磁盘，再确定容器资源限制。文件、缓存、日志和正式交付分别管理，不用统一删除策略代替容量治理。

## 阶段三：OpenRig 长期部门独立试点

补 tmux 和所选员工 Harness，使用独立的用户配置、队列库和仓库副本，验证经理、开发、QA 三岗位的持久身份、待办、交接、会话移交及重启。

先实测当前 Go 模型与 DSH/Pi 接入成本；固定源码的 workflow 语法仍有限制，不能直接替换已验证业务门禁。试点结果决定谁成为唯一派发者；另一系统提供执行或观察能力，不能同时自主派发同一任务。[选型报告](research/openshell-openrig-reuse-2026-10-08.md)

## 持续运行与交付要求

持续运行需要处理电源/合盖/休眠、开机启动、健康检查、备份、磁盘容量和故障恢复。软件服务在线不等于所有员工持续调用模型，无待办时应待命。

各阶段记录软件版本、提交 SHA、配置与路径、实际测试输出、Run ID、费用和故障；完成、失败、跳过及未知结果分别标明。跨机器数据/凭据迁移与 7×24 稳定运行目前均未验证。
