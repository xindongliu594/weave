## Findings and contract checks

1. **A2/D2 dependency order is acyclic.** A2 Task 7 explicitly consumes D2 Tasks 1–2, which supply the shared append/outbox/failure interfaces; D2 Task 3 consumes the later A2/C1 business-boundary integration. D2 boundary clause 4 and its final self-check now say the same thing. A2 Task 7 and resource-authorization spec flow clause 5 both use `projectAuditOutbox` and the shared `audit_run_projection`, with thin `human-audit.ts` adapters. There is no requirement to complete all of A2 before starting the D2 foundation.

2. **One canonical audit path and one operation path.** D2 Task 1 extends `human_audit_events` and preserves legacy `appendHumanAudit`; event plus outbox insertion is atomic even for a standalone legacy audit call. Business success must still use its own transaction client. Task 2 projects at most 100 canonical events per short transaction, commits the projection and publication marker together, bounds the rebuildable projection, and never writes active JSONL. C1 remains owner of the existing `local_operations` row/operation identity and effect transitions; D2 Task 3 only validates and appends audit inside those transactions. SQL canonical merge, effect evidence, telemetry delivery, and billing remain distinct.

3. **Current authority and actual actors are separated correctly.** A2 supplies current server-side resource/department authority, including epoch revocation, before each newly admitted effect. D2 treats authority snapshots as evidence rather than permission. HTTP actor comes from the authenticated principal, not request fields. Background execution is `system`, employee/session belongs to execution attribution, the original person is linked through `requestedByAuditId`, and a device receipt remains a device event. Unauthenticated attempts cannot claim a human; revoked late evidence is recordable without authorizing dispatch or merge. The new action union must enforce the stated current-authority requirement for newly successful effects.

4. **History/restore requirements are explicit gates, not an assertion about existing backup safety.** D2 preserves schema-1 history and null legacy attribution, retains application append-only audit enforcement, and makes same-ID/different-content restore a conflict. Task 8 requires destination history preservation, immutable identity-reference matching, valid FK order, and coordinated A2/F1 restore before passing the gate. Actual `identity-schema.ts` currently has an audit-to-department FK and UPDATE/DELETE protection; actual `backup.ts:61` still executes wholesale `TRUNCATE ... CASCADE`. The added Restore acceptance paragraph explicitly bans that old path for a destination with audit history and requires preserving referenced user/department identities or refusing before destructive SQL. This matches the inspected FK/trigger behavior. No existing restore path was approved by this review.

5. **External summaries exclude raw content by construction.** Tasks 4–5 use a fresh bounded scalar allowlist, known event/phase/reason enums, registered capability identity, and no prompt/stdout/arguments/free-text error traversal. External actor is kind only. Raw provider account/request IDs, human identity/session credentials, filenames/paths, and parameter hashes remain excluded. Actual `trace.mjs:65` generates the runtime model request UUID locally, so mapping that field to `modelRequestId` need not expose provider request IDs. Trace observers run only after durable append and cannot change its outcome. OTLP remains opt-in, disabled mode performs zero transport/provider construction, queues and shutdown have explicit fault-test bounds, and delivery cannot authorize effects or settle money.
