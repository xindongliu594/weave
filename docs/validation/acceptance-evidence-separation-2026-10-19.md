# 开发自检与独立验收分离

## 调研与原因

已有真实 A/B 记录见 `planning-ab-2026-10-19.md`：三份强化阶段提示的回答仍将功能标准绑定到 `node --check`。原始回答保持不变。当前提示要求每个 verify 都覆盖全部标准，网页又将第一条命令默认填入全部标准，形成错误诱导。

- [Node CLI](https://nodejs.org/api/cli.html#-c---check)：`--check` / `-c` 仅检查语法，不执行程序。
- [Promptfoo assertions](https://www.promptfoo.dev/docs/configuration/expected-outputs/) 与 [LangSmith evaluation](https://docs.langchain.com/langsmith/evaluation-concepts)：确定性检查和内容质量评审分开；不能自动解决为伍任务合同的证据绑定。
- 核对现有 DSH 0.1.5-rc.1、[插件目录](https://dshplugin.app/plugins)与 [agent-teams](https://github.com/NanmiCoder/dsh-agent-teams)：沿用工具执行、交接和审查机制，本次不引入另一套评测引擎。

## 已授权实施计划

1. 新方案中禁止把可识别的独立 Node 语法检查作为 acceptanceChecks；保留在 verify。实现/修复节点可仅有语法自检且不填写命令映射，但必须有读取全部产出的后续独立 QA，其实际命令映射由现有合同校验。其他执行节点仍需要映射。
2. 改正提示与结构示例；网页取消自动填第一条命令、排除语法检查作为验收选项；历史语法证据明确显示范围。
3. 先写失败回归，再实现；重放三份真实回答、验证开发自检仍受宿主强制、独立功能测试能发现语法检查发现不了的问题。运行相关回归、类型检查和构建，独立审查后发布 JJ 并保存证据。

边界：不猜测自然语言标准，不解析任意 shell 脚本的语义，不改历史合同/回执/恢复哈希，不删除已有数据。任意测试是否覆盖真实需求仍由独立 QA、经理及测试审查负责。当前阶段不发起新付费模型请求。

## 进度

- 调研、现有接口核对完成；实现前已确认 verify 在无 acceptanceChecks 时仍由宿主强制执行。
- 程序修复、回归、独立审查、JJ 发布及浏览器核对完成。修复后新提示下的真实模型生成尚未复测，不能以本轮离线回放代替真实模型验收。

## 实际修改

- 新模型方案拒绝把可识别的直接 Node `--check` / `-c` 命令作为逐项功能证据；实现/修复的语法自检仍保留并由原宿主强制执行，必须有独立后续 QA 消费全部产物并提供实际命令映射。
- 提示词、结构示例与网页取消“所有标准自动绑定第一条命令”。仅有语法命令时不能启用功能映射；旧错误映射会显示提示。
- 补齐旧版模型草案确认入口的再次校验，防止用户编辑后绕过对话校验；重复确认已保存项目保持原语义。
- 历史运行中的语法通过明确标注为语法证据，不修改数据库、原始回应、收据、合同哈希或恢复记录。

JJ 共 154 项检查通过。三份未经修改的真实 A/B 回答全部被新增规则拒绝；实际 Node 反例是明确标记的本地测试夹具：恒返回 0 的实现语法检查退出 0，0°C→32°F 功能测试退出 1，宿主拒绝 QA 交接。省略 acceptanceChecks 不能省略开发实际执行的 verify。

验证中发现并处理：

1. 首轮 Windows API 回归受沙箱本机端口 EACCES 阻挡，允许本地连接后使用同一隔离数据库测试通过；最初误以直接 test 命令启动需数据库的套件，改用仓库既有集成驱动。
2. Node 子测试继承 `NODE_TEST_CONTEXT` 会影响执行，测试驱动只在子进程环境中移除此变量，真实失败断言通过。
3. 独立审查发现 `node --require node:fs --check file` 绕过识别，先复现失败再修正有限的 Node 参数解析。审查没有其他重要问题。
4. API 测试发现旧模型草案确认入口缺少同一校验，先复现保存错误方案，再修复并验证合法方案仍能确认、不启动员工执行。
5. 扩展回归中的旧合成夹具仍绑定语法检查，已只修改明确标记的反事实夹具；原真实回答保持原样。初次失败保留在 `related-api.txt`，最终同一套件 20/20 见 `related-api-final.txt`，另 3 项确认检查记录于前者。
