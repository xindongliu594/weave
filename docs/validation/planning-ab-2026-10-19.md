## 设计

- 同一摄氏转华氏需求、相同六条历史消息、工具/文件/员工模型目录及 4000 输出上限。每个请求独立，不把本轮答案反馈给下一次。
- A 完整复用上次实际请求；B 仅在首条 system 末尾追加阶段边界说明。原员工目录保持不变，替换的是规划请求的后端模型，不是拟议员工的模型。
- DeepSeek V4.1 Flash、GLM-5.3-Flash 各 A/B 三次，固定交错顺序，不因结果好坏追加调用。两者均保持 thinking disabled、JSON 输出，无 seed/temperature 覆盖。
- 这是多轮纠错现场的重采样，不能外推为所有新需求的首轮成功率；每格 n=3 只能发现问题，不能证明稳定性或因果。
- 先检查 schema、生产合同校验，再逐份核对阶段文件可用性、开发自检与功能验收是否混淆、独立 QA/经理、一次返工与模板是否一致。校验通过不等于执行通过。
- 无效方案也是结果，不修正文档伪装成功。传输、截断或未知费用出现即停止整组；已结算用量照实记录，不自动重放。

人工复核仍发现两项说明与结构不一致：

- 回复声称测试文件“绑定 QA 自己的验证任务”，实际交付映射由经理核对开发和 QA 的文件。结构合理，解释不准确。
- 回复声称总估算约 $0.24。按返回的任务 Token 与固定单价，基础估算 $0.0495，含 20% 余量为 $0.0594；任务金额上限之和 $0.17，也不是 $0.24。不能把模型自然语言的金额当作账本或预算依据。

原提示后两次分别缺少开发 verify、漏掉一条验收标准的命令映射，程序正确拒绝。阶段说明版三份虽通过静态合同，却全部把“导出指定函数”或“非法输入抛错”绑到 `node --check src/temperature.js`；该命令只检查语法，无法证明这些标准。第二份还在文字中声称 review_repair，而结构化 template.id 是 pipeline。

本地反例使用明确标注的测试字符串（不是员工交付物）：语法合法但恒返回 0 的函数通过 `node --check`，检查 0→32 的行为断言失败；见 `syntax-counterexample.json`。不能把模型填满字段、检查命令返回 0，当作功能验收成功。

因此，**同一输入的输出存在变化，原错误不是必现；明确阶段边界在本次小样本中改善了结构完整性，但没有解决证据语义问题**。每格仅 3 份，且 GLM 阻塞打断了原交错顺序，不能估计稳定错误率、证明因果或比较模型优劣。程序的文件依赖校验仍须保留。

本次定位到的产品缺口：目前校验能检查命令是否存在、文件是否可用、标准索引是否覆盖，却不能确认命令是否证明自然语言标准。后续应先把开发完成条件和最终功能验收条件分清，再研究现有结构化验收/eval 的复用方式；不能继续靠增补提示句或让模型自称已检查来代替证据。这是后续修复方向，本轮没有部署新的语义判断器。
