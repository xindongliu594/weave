## 实际改动

复用已安装的 `fs-native-extensions@1.5.1`、现有原生文件锁、AsyncLocalStorage 写入作用域，以及 DSH 原有持久化流程。没有新增依赖、锁引擎、恢复引擎或插件格式。来源调研沿用 [既有锁方案比较](../research/task-recovery-writer-fence-2026-10-21.md)，实施依据是 [原写入隔离计划](../superpowers/plans/2026-10-21-archive-writer-fence.md)。

- 应用启动登记档案根，登记后不可解除。create/open/append 必须处于同一运行的有效写入作用域；登记前的原始句柄、已结束或其他 owner 的句柄不能借新的持锁机会继续写入。
- 日志创建、打开时校验、去重、序号分配、追加、fsync 和游标更新共用已有同步 journal 锁。两个进程不能各自分配同一个序号。
- Checkpoint SHA 对象写入要求匹配的 writer；日志压缩要求 maintenance。真实物理写入出错时，即使上层捕获异常，也保持失败占用。未登记的独立离线夹具仍使用原接口；它们不构成生产隔离证据。
- 修复已确认取消被错误归为本地持久化未知的问题：只有原始 SQL 取消收尾成功返回，才给执行器内部的取消结果。已开始的设备操作仍是 `cancelled / started=true / result=null`，外部结果待核对，不自动重放；未知 COMMIT、回滚、任意无来源的错误仍保留阻断。

底层断言没有替代应用授权、预算、设备回执、CAS 或企业模式门禁。

## 失败、修正与限制

1. 最初受限环境将临时目录映射到不存在的虚拟路径，两次执行没有进入有效断言。这不是 RED 证据；随后普通本机环境的 `red-native.txt` 才是有效的 6 项失败。
2. 第一轮产品组合命令在取消后暴露 writer 被错误锁死，后续场景受影响，300 秒超时。修复后取消两项、执行器全文件均通过，原失败保留。
3. API 分页夹具先后存在未持锁建档、以及在结束作用域后用旧句柄写 Checkpoint；分别改成测试的真实 writer 作用域和新打开句柄。没有放宽生产门禁。最后整份 API 14/14 通过。
4. 第二次完整产品文件有 14 个场景通过，返工两个场景超过原 25 秒 helper，整个文件达到 300 秒上限。只扩大返工测试 helper 到 45 秒和对应测试到 60/180 秒；业务预算、调用次数和生产时限不变。另一次 6 场景命令退出 0，覆盖两项返工和四项恢复，耗时约 273 秒，其中单个返工成功场景约 35 秒、四个升级分支合计约 76 秒。
5. 两份产品日志去重覆盖全部 19 项，但**没有声称完整单文件命令最终退出 0**。原失败和超时仍在清单；其他已通过场景没有无理由重跑。
6. 构建的首次受限进程长时间停留在 TypeScript 检查，已核对 PID、父 PID、启动时间和工作区路径后停止。普通本机重跑结果单独记录，不把主动停止记为成功。

## 独立审查与决策

`/root/archive_trace_cutover_review` 只读审查：Critical 0、Important 0。一项非阻断建议暂缓：为登记根的真实物理写/fsync 失败新增“上层捕获后，另一进程仍不能拿到 source”的直接回归。已有通用失败占用测试和代码检查不能冒充这个精确用例。

本批决策与代价：

- 显式登记生产根，保留离线未登记夹具兼容性；代价是漏接的生产 writer 会被拒绝，须靠调用方回归发现，不能宣称所有原始 FS 路径都已覆盖。
- 已确认取消不再锁死本地写入，但设备未知状态继续存档；代价是必须严格保持“原始 SQL 已确认后才产生内部结果”的顺序，未知事务仍阻断。
- 只调整实际变慢的测试窗口；代价是 Windows 本机回归更慢，记录实测时间，不改变业务额度。
- 完整来源认证、子运行初始化、企业模式、真实模型、JJ 部署和全仓库结果均未在本批完成；保持这些门禁，代价是还不能宣布企业恢复可用。
