## 审批与真实调用

自动审批拒绝了最初 launcher 读取生产 API `/proc/.../environ` 的尝试，理由是可能提取数据库凭据；该脚本未执行。已移除该读取路径后完成上述零调用检查。

真实规划需要可信 broker 取得现有后端的运行配置以复用费用与凭据链路。现有网页 API 没有通用的带预算 completion 入口；未使用组织规划接口伪装 Cortex 调用，也未复制 Key 到 Windows。

用户随后明确答复“允许，按上述边界完成真实规划”。按此授权，只在 JJ 读取唯一为伍 API 进程的 `DATABASE_URL`、`DATA_DIR` 两个配置值，内存传给可信 broker；不输出、落盘或传给插件。之后的工具审批通过，两次真实调用已完成，原阻塞已解除。

任务拆分覆盖了主要需求，产出 schema 也较具体。但这仍是候选草案，未通过可执行编排验收：

1. **依赖未落实。** 六个节点全部 `depends_on: []`。调用原版 `dependencyLevels`，六节点确实被分到同一层，而非“开发后 QA、QA 后经理”。本轮未执行节点，因此没有实际乱序执行。
2. **角色仍是文字。** 没有具体员工绑定、独立 QA 身份校验或为伍授权映射。T0.1 只是要求未来生成这些内容，并非已完成组织方案。
3. **未决定并行模式。** 要求后续节点产出 `parallel_work` 不等于目前已给出可并行的关系。
4. **另有原版分层问题。** 零模型反例 `A、B 无依赖；C 依赖 B；D 依赖 C`，期望 `[[A,B],[C],[D]]`，实际 `[[A,B],[C,D]]`。固定版 `lib/service.js:9102` 的 `deps.delete(...ready)` 只删除首个参数，后续被当作异常环一起放入末层。该反例独立于本次模型输出，未修改上游代码。
