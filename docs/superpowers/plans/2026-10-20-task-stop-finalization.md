## Success and bounded finalization

Task-profile preflight requires trusted `finalizeAccepted` before prepare/model/tool effects. Legacy execution does not acquire this requirement. After all host-accepted nodes, settled original model requests and successful durable final team checkpoint, establish business acceptance. A missing/failed final checkpoint is a business failure; it grants no cleanup authority.

Call `LocalRunExecutor.finalizeAccepted(signal)` at this boundary before host close/run finished and while SQL still has the original running owner/lease. The source-only lifecycle entry first proves every currently approved native node completed with its own durable v2 accepted boundary and no unresolved operations, then uses the same exact-key source verification/CAS/provider chain. It never fabricates an active target or changes activeTaskAssignment. Every new effect rechecks current permission, lease, frozen provider methods and relevant source identity immediately before dispatch.

The finalizer has a 120-second shared maintenance signal starting at method entry (before provider selection, SQL pool acquisition or queue wait), combined with the run cancellation signal, and dispatches serially, at most two fresh stops (the unchanged running-capacity bound). More source candidates than this is protected `TASK_STOP_FINALIZE_LIMIT`, not permission to widen capacity. Stop on the first uncertainty/error. The provider must expose trusted `acceptedStopCapabilities()` returning exactly `{version:1,deadline:'shared-abort-v1'}`; freeze and compare this method reference and response along with original provider identity. Legacy absence fails task preflight, not type construction. Function arity/options alone are not deadline support.

Extend the existing `maintenance(fn)` queue with optional signal-aware admission, not another queue. Before start, the queue entry has one irreversible pending/started/cancelled latch. Aborted pending entry is marked cancelled before rejecting its caller, removes its listener, and is skipped when the original queue reaches it; it can never later call fn/beforeDispatch/create an intent. Started entry removes the pending-only listener and awaits its cancellation-aware fn; no caller-side Promise.race may abandon a still-dispatchable effect. Every continuation and beforeDispatch boundary rechecks the same signal. Existing callers without an optional signal preserve their queue behavior.

Private signal signatures preserve old positions: `maintenance(fn, signal?)`, `stopAcceptedTask(key, expected, beforeDispatch, signal?)`, `reconcileAcceptedTaskStop(key, identity, signal?)`. The signal is a trusted in-process AbortSignal; it never enters expected identity, HTTP or journal. Old no-signal accepted-stop calls select one fallback 120-second signal at entry and reuse it through observation. API/runtime owns the finalizer's combined outer signal; optional arguments never substitute for the required capability handshake.

Device stop and observation combine this remaining signal with existing local transport limits and pass it unchanged through admission, stop and original-ID observation instead of granting observation a new 120 seconds. Check it after beforeDispatch before fsynced journal intent. A local CLI aborted after dispatch retains unknown intent; cancellation cannot undo the remote operation. Await local transport termination/settlement, not remote success; never replay or release capacity from timeout. SQL pool acquisition must have bounded cancellation: a late-acquired client after abort is released before BEGIN, never executes fn. Each transaction sets local statement/lock timeouts to no more than remaining budget, and after COMMIT the signal is checked before callback return. COMMIT acknowledgement uncertainty never authorizes a fresh closure. Missing deadline propagation is failed preflight, not fake timeout success. Tests hold queue/pool/transport independently beyond deadline and establish caller completion plus zero later effect for pre-dispatch cancellation.

The original business deadline still governs work/settlement/final checkpoint. After this durable business boundary, stop the business timer; only the bounded maintenance signal governs cleanup. This grants no further model/tool/business work or budget. Finalizer returns `{version:1,state:'stopped'|'pending',reasonCode?:<bounded code>}`; the authoritative per-scope facts are re-read from SQL, not supplied by this return value.

Expected maintenance errors (deadline/cancellation/lease or provider change/binding denial/response loss/SQL uncertainty) yield completed business acceptance with pending maintenance. They cannot roll back acceptance or rewrite it as failed. Errors before the durable boundary retain original business failure behavior. Serialization/archiving failure is never described as fully recorded success; SQL projection must still reveal the protected scopes.

Teardown is distinct from stop: after the durable boundary, synchronously close model/tool/employee admissions before awaiting the existing idempotent host.close. Await teardown at most 10 seconds; it grants no business operation. If a plugin/handle does not settle, retain the single original close promise and Host reference, attach eventual settlement handlers, set existing runtime readiness to degraded and reject new launches while teardown is unresolved. Do not detach it silently, start a second close, erase active state or claim resource release. The bounded completed business result carries pending maintenance; late close cannot rewrite it. This limited bounded wait is safe only after all business admissions are fenced; it is forbidden around provider stop/dispatch. Finally must not await the same hung close again or throw expected post-acceptance close errors over the result. Earlier business errors keep their original classification. A hanging-close test must verify no model/tool effect/new launch after the fence and readiness recovers only after that same promise settles. No second scheduler or persistent cleanup queue is introduced.

The synchronous Host seam is a trusted `stopAdmission()` calling existing adapter/employee admission stops plus a closed flag in the existing task-tool-boundary DSH guard and registered-body wrapper. Both fresh and already-admitted exec bodies reject after the fence, including late plugin registrations. This extends the existing final guard instead of replacing DSH dispatch. Tests must include an already-guarded exec held across the fence; merely stopping employee spawning is insufficient.

## Durable projection; no second lifecycle store

Add a strict read projection `TaskStopMaintenanceV1` from exact task scope rows, strict accepted_stop records and authenticated archived accepted/checkpoint evidence. No extra status table. Shape: `{version:1,state:'not-applicable'|'stopped'|'pending',scopes:[entry]}`. A verified-identity entry is `{key,sandboxId,workspaceRevision,state:'stopped'|'prepared'|'dispatching'|'unknown'|'no-intent',stopId?:uuid,reasonCode?,canReconcile:boolean}` with exactly validated full key/ID/revision. An unverified entry is exactly `{state:'unverified',displayKey,reasonCode,canReconcile:false,key?:<validated full key>,sandboxId?:<validated ID>,workspaceRevision?:<validated SHA>}`; missing fields stay absent, never fabricated or coerced. displayKey is a non-effectful deterministic SHA of validated runId plus row locator or archived accepted task locator, not a dispatch key. If even that locator is ambiguous, use one run-level aggregate unverified entry with a bounded count and generic reason. Whole run/every list is bounded; malformed/truncated/missing rows despite archived acceptance produce pending/unverified, never stopped from an empty list. Legacy profile alone is not-applicable. Tests cover missing sandbox identity, malformed marker, missing SQL row with archived acceptance and duplicated locators. Unverified entries never enable reconciliation.

The aggregate's exact variant is `{state:'unverified',displayKey,reasonCode,unresolvedCount:<positive bounded integer>,canReconcile:false}` without effect identity fields. None of these unions allow unknown properties. Duplicate keys/ambiguous locators are aggregated rather than rendered under duplicate React keys.

Only a validated stopped marker projects stopped. A historical accepted scope with NULL marker is `no-intent`; missing/inconsistent accepted proof is `unverified`. Do not manufacture stopId, stopped result or free capacity. Any prepared/dispatching/unknown marker remains pending, even if a warning event was lost. Only an existing marker can expose reconciliation; no-intent has no retry-stop button in this slice. The last partial workspace revision is not the full canonical revision.

Include this projection in GET `/api/runs/:id` and GET `/api/storage/sandboxes` exact-key task rows. Run summary includes bounded `runtime/maintenance-pending` and `runtime/maintenance-completed` observations, but neither is authority. Cache-free SQL projection covers failures before intent, after effect before acknowledgement and before warning/run-finished append. Existing recover may preserve terminal business state or mark interrupted; it never creates a fresh stop under a recovery lease. Restart re-reads projection; a human may reconcile an original intent only. History archive remains readable; a missing archive fails observation closed and remains visibly unverified.
