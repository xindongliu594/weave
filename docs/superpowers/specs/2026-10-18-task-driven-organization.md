# 为伍：按任务组织团队与交付质量设计

日期：2026-10-18。状态：待实施设计；本轮没有修改产品代码、部署 JJ 或新增付费调用。

2026-10-19 后续记录：第一段的办公交付和受控重启已验收，首次规划质量仍未通过，见[实际报告](../../validation/task-driven-organization-real-acceptance-2026-10-19.md)。用户要求五种以上编排，后续模板范围已扩展为[七类编排接入设计](2026-10-19-orchestration-pattern-library-design.md)；本文件的三个初始分类不再代表后续模板数量上限，当前生产能力不因此改变。

## 产品目标与本次边界

用户提出任务，为伍先明确交付标准，再推荐适合的协作方式和人员。用户可以通过对话调整，确认后才创建或变更组织、创建项目。员工执行、独立检查、经理验收均围绕这份确认过的目标；成功的组织方式可以随后沉淀为版本化模板。

部门是长期保存人员、权限和知识的组织；项目团队是某次任务实际参加的员工；任务图表达本次如何合作。三者分开保存。同一个部门可以串行或并行工作，跨部门成员也可以参与同一任务图。

本设计分三段交付：

1. **近期实施范围：任务驱动的组织推荐 + 交付标准。** 支持选择已有主部门、挑选其成员、借用已授权的其他部门员工；没有合适部门时走现有新部门草案与确认。选择理由、人员来源、DAG、验收映射一并保存。用户无需先指定编排名称。
2. **随后独立实施：编排模板发布与检索复用。** 先完成第一段真实验收，再从已验收方案提炼角色与协作规则，通过现有知识版本和候选审核生命周期登记。模板检索结果进入同一规划入口。
3. **后续能力：运行中较大范围重规划、临时组织。** 单独设计版本切换和权限审批。第一段仅沿用已存在的受限返工，不宣称支持任意更换运行中成员、多个经理或无限递归团队。

第一段限制保持：一个项目恰好 1 位经理、最多 6 位员工（含经理）、最多 50 个计划任务、子团队深度 0；返工轮数仍受既有 0～2 及实际策略约束。没有为了使用新功能增加模型或基础框架依赖。

原生 Profile 的种子任务字段不足以承载为伍完整的验收、文件和预算合同，且 `profiles` 不是公共子路径导出。继续通过现有 `stageApprovedTeam()` 创建完整合同任务；不深路径导入、不建立第二套调度器。上游新版本功能不算当前已安装能力。

## 用户流程与推荐规则

```mermaid
flowchart LR
  A[需求对话与交付标准] --> B[读取可见人员和获授权能力]
  B --> C[AI 推荐协作方式和团队]
  C --> D[程序核对人员 权限 DAG 预算 验收覆盖]
  D --> E[网页展示并由用户确认]
  E --> F[现有 DSH 执行与受限返工]
  F --> G[实际证据 独立检查 经理验收]
  G --> H[后续阶段：提炼并审核发布模板]
  H -.检索版本化方法.-> C
```

推荐用现有需求/方案规划调用完成，不为每个任务固定增加一个路由 Agent 或额外模型请求。普通组织对话沿用现有对话账务方式，不改成项目执行费用；正式规划与执行沿用现有授权、收据和费用规则。

先提供三个可解释的协作起点，允许模型按任务生成不同节点及依赖：

- 简单交付：一位执行员工完成材料，程序检查可机械验证的项目，经理检查业务结果；需要独立专业判断时必须增加合适检查者。
- 顺序交接：前置成果完成后交给下一角色，再做独立审查与验收。例如实现 → QA → 经理。
- 并行汇总：互不依赖的工作并行，汇总节点等待所有必需分支，再独立核对。例如资料检索与数据整理 → 报告 → 复核。

这些是规划指导，不是三条写死的任务流程。简单任务不强制多人分拆；技术或质量依赖不能为了并行删除。没有合适员工或工具时返回明确缺口，不创建无授权员工，不把有缺口的方案标为可执行。编排模板库尚未上线时展示“新方案”，不能假称命中了历史经验。

## 最小数据与接口变更

### 草案与人员选择

扩展组织候选为显式 V2 封套，保留现有 V1 `{department,rationale,tasks}` 读取与旧确认流程。V2 分为：

- `target.kind = existing`：`departmentId`、`departmentVersion`、`primaryAgentIds`、`collaboratingAgents[{departmentId,departmentVersion,agentId}]`。
- `target.kind = new`：沿用新部门定义。首期不在新部门草案同时借用外部员工，避免创建与跨部门绑定合成更多分支；可先创建后通过已有部门入口组队。
- 共有：`schemaVersion:2`、`rationale`、`tasks`、`orchestration`、`deliveryCriteria`。

`orchestration` 保存 `pattern`（`single` / `pipeline` / `parallel`）、选择理由；不保存第二份 DAG。将来模板引用单独增加不可变版本/hash，不把当前模式标签当成已发布模板。

组织目录从当前登录用户可见、未归档部门读取，只提供选人所需的 ID、版本、岗位、能力摘要和项目授权范围。模型只能引用目录中的身份；`sourceDepartmentId/sourceAgentId`、凭据、权限及运行身份均由后端重新构造。目录读取不自动获得知识正文或工具执行权限。

已有部门候选中任务 assignee 使用既有项目 ID 规则：主部门为原员工 ID，借用员工为 `${departmentId}::${agentId}`。新部门候选使用草案中的员工 ID。程序拒绝不存在、重复、混淆的身份。

扩展 `buildProjectTeam` 的可选主部门成员筛选参数：旧调用不传时维持原有“包含主部门全员”；新调用只纳入选择的主部门员工，必须包含原主部门经理。借用员工仍为 member，总人数仍最多 6。不修改部门本身员工名单，不扩大员工授权。

新候选保存在现有 `organization_previews.data`，确认在同一事务锁定草案及来源部门、核对版本、构造团队并校验方案，成功才写项目/必要的新部门；重复确认返回同一结果。部门已删除、员工已撤销、版本变化或权限收回时，草案失效并提示重新规划。已有“更新部门”入口语义保持，不将项目选人误当成部门人员编辑。

### 交付标准与执行方案

`Plan` 增加可选 `orchestration` 和 `deliveryCriteria`，老计划不补造证据。新 V2 草案必须有交付标准，每条包含：

- `id`、`description`：用户可确认的一项具体要求。
- `producerTaskIds`：谁产出该结果。
- `checkTaskId`、`checkCriteriaIndexes`：由哪个任务的哪些既有验收条目检查。
- `independent`：是否要求检查者与生产者不同；高风险或用户要求独立检查时为 true。

实际可执行图唯一来源为 `Plan.tasks`。已有 `validatePlan` 与 task contracts 继续作为机械校验入口，增加：引用完整、检查依赖产出、每条要求有检查、独立检查身份不同。任务自身 `acceptanceChecks` 保持原有覆盖规则和可核验检查机制。

这些字段能阻止遗漏检查和伪造结构，无法凭程序证明需求语义已全面覆盖。因此草案展示原始需求与交付标准，用户确认后封存目标；QA 核对内容，经理核对完整需求与证据，不能仅凭员工说“完成”通过。

## 质量如何落地

| 要求类型 | 实际证据 | 独立核对 |
| --- | --- | --- |
| 程序功能 | 测试命令、退出码、断言、报告及被测文件 hash | QA 执行与分析测试；不能以语法检查代替功能测试 |
| Word/表格等资料 | 插件生成的实际文件、结构与内容检查、必要的渲染检查 | 核对用户要求、数据来源、格式和可打开性，不能只核对文件存在 |
| 研究/总结 | 来源、引用、数据与结论对应关系 | 检查事实支持、遗漏和不确定项；模型评分作为辅助判断 |

经理输出逐条通过/失败/未验证，并关联当前版本证据。必需检查失败或缺证据时，整个项目不能自动宣称验收成功。修复保持原任务目标、权限和预算；超过受限返工范围则停止并展示需要的变更，不让模型自行删掉质量要求。

重启读取原确认方案和人员/知识/能力版本；不重新路由、不换模板、不重跑已完成任务。未知外部操作继续沿用现有核对机制。后续大范围重规划必须单独生成方案版本和审核差异。

## 后续模板沉淀的边界

第二段再实现“候选 → 验证 → 发布 → 检索 → 新任务绑定”。复用知识文档、不可变版本、ACL 和现有候选审核模式；明确扩展结构化类型后再存储，不能假定现有 knowledge source 接受任意模板元数据。

模板保存角色能力要求、协作关系、质量规则、适用/排除条件与成功/失败证据，不携带原员工身份、凭据、旧结果或旧完成状态。公司能力目录可发现模板，但它不伪装成可执行 Skill/MCP。没有引入新图数据库、插件引擎或向量库的需求。

复用分别统计规划与执行耗时、Token、费用、通过率和返工次数；匹配任务规模、模型、缓存及权限条件后比较，样本不足或未提速据实显示。

## 第一段验收与完成定义

1. 用简单资料、顺序研发、并行研究三类小需求检查推荐；不是强求唯一模式，而是检查依赖、合适角色、必要独立检查与说明是否合理。
2. 本地测试覆盖无合适员工、权限不足、伪造来源、并发修改部门、重复确认、失效草案、写同一文件冲突、检查与产出无依赖、作者自验冒充独立 QA、旧计划兼容。
3. 故意放入一个缺交付和一个坏产物，确认系统拒绝成功或要求返工；仅使用模型主观“通过”不算质量证据。
4. 一个小型真实任务通过网页从需求、推荐、修改、确认到员工生成产物、独立核对、经理验收；原版插件负责业务产物，Codex 不补写交付文件。
5. 同一方案进行一次受控中断/重启，确认人员、目标、DAG、费用与文件版本保持，完成节点未重跑。优先复用已有验收项目可用成果，但新功能的新方案必须实际走过新入口。
6. 所有真实调用提前核对仍可用于该项目的授权与完整请求余量，沿用金额、次数及未知预留；本设计不新增费用授权。

保存运行 ID、方案版本、真实证据位置、正反例结果和最少必要网页截图。未通过项目明确标为未验证/失败/受阻。第二段模板复用与第三段运行中重规划不能计入第一段已完成功能。
