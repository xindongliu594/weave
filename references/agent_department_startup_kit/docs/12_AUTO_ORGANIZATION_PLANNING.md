# 12 主模型自动组织规划

## 目标

用户可以只提交项目需求和资源上限。主模型根据真实模型目录生成一个候选组织方案，普通后端代码完成硬校验，用户批准后才创建 DSH Agent Team。

## 三种模式

| 模式 | 规划 | 批准 | 适用用户 |
|---|---|---|---|
| `recommended` | 主模型生成 | 用户查看、编辑并批准 | 默认 |
| `automatic` | 主模型生成 | 仅低风险、低于阈值且校验通过时自动批准 | 熟悉系统的用户 |
| `custom` | 用户配置 | 仍需系统校验 | 高级用户和固定流程 |

## 输入

规划器接收四类输入：

1. ProjectRequest：需求、目标和期望交付物。
2. ExecutionPolicy：预算、人数、并发、时限、工具和权限硬上限。
3. ModelCatalogSnapshot：真实可用模型、能力、价格和状态。
4. KnowledgeCatalogSnapshot：可授权知识库及其层级。

规划器不得接收 API Key 明文。

## 输出

主模型必须输出符合 `organization-plan.schema.json` 的 JSON：

- 是否需要多 Agent 及理由。
- 部门名称和目标。
- 经理与员工角色。
- 每个角色选择的模型目录 ID。
- 员工工具、知识库和预算分配。
- 任务、负责人、依赖和验收标准。
- 预计 Token、费用、时长和风险。
- 预算不足时的降级方案。

## 两阶段执行

### 阶段一：规划

- 只允许读取模型目录和知识目录。
- 不创建员工、不执行任务、不调用外部写工具。
- 规划费用计入单独预算。
- 结构化输出解析失败时最多修复一次。

### 阶段二：执行

- 只有批准且校验通过的方案才能转换为 RunSnapshot。
- Runtime 使用批准时的模型、权限和知识授权快照。
- 执行期间允许减少权限或停止，不允许静默扩大约束。

## 确定性校验规则

校验器必须逐项检查：

- JSON Schema 合法。
- Agent 数量、并发、截止时间不超过策略。
- 每个 `modelCatalogId` 存在、启用且凭证可用。
- 模型能力覆盖任务所需能力。
- 工具、知识库和网络权限都是策略允许集合的子集。
- 任务负责人存在，依赖引用存在，DAG 无环。
- 每个任务有目标和验收标准。
- 后端按价格目录重算的费用不超过预算。
- 自动模式不包含必须人工批准的高风险操作。

校验返回：

```json
{
  "valid": false,
  "errors": [
    {"code": "MODEL_NOT_ALLOWED", "path": "/agents/2/modelCatalogId"}
  ],
  "warnings": [],
  "recalculatedEstimate": {"currency": "USD", "total": 12.4},
  "validatedAgainst": {
    "policyVersion": 3,
    "modelCatalogVersion": "catalog_20260914_01"
  }
}
```

## 模型选择建议

- 规划/经理：优先推理、工具和长上下文能力。
- 编码：优先代码生成、工具调用和结构化输出。
- 搜索/整理：可优先低成本模型。
- 独立验证：尽量与实现 Agent 使用不同模型或不同上下文。
- 小任务应优先单 Agent；多 Agent 需要给出明确收益理由。

## 用户编辑与版本

- 每次重新生成或编辑都创建新 PlanVersion。
- 页面显示主模型原始方案、用户改动和校验结果。
- 修改角色、模型、工具、知识库、预算分配或任务依赖后必须重新校验。
- 批准请求带 `planVersion`，避免批准过期方案。

## 费用控制

主模型估算仅用于建议。后端根据目录价格、预计 Token、轮数和并发重新计算。运行时以实际用量为准，达到硬上限后停止启动新模型调用。

建议默认分配：规划 10%、执行 70%、验证 15%、重试预留 5%。这些比例不能突破用户总预算。
