# 08 技术验证、测试与验收

## 开工前 DSH Spike

在开发正式 UI 前完成以下验证。每项保存版本、配置、日志和结论。

| 编号 | 验证项 | 通过标准 |
|---|---|---|
| S01 | 代码创建团队 | 不依赖自然语言猜测，能稳定创建 Captain 和 3 名成员 |
| S02 | 成员独立模型 | 3 名成员分别使用不同 Provider/Model，日志可证明 |
| S03 | 角色隔离 | 三个角色按各自职责输出，不共享未授权工具 |
| S04 | 任务 DAG | 未满足依赖的任务不会提前运行 |
| S05 | RAG 权限 | 员工无法检索未授权部门知识 |
| S06 | 停止 | 用户取消后 10 秒内不再开始新模型调用 |
| S07 | 重启恢复 | Runtime/API 重启后能恢复或明确进入可处理状态 |
| S08 | 并发写 | 两个 Agent 不会静默覆盖同一文件 |
| S09 | 用量 | 每次调用可归集到 Run、Agent 和模型 |
| S10 | 升级隔离 | 业务层只调用 Adapter，不导入 DSH 内部类型 |
| S11 | 自动规划 | 主模型稳定输出符合 Schema 的部门、员工和任务方案 |
| S12 | 虚假模型 | 主模型选择目录外模型时被校验器拒绝 |
| S13 | 预算越界 | 人数、并发或预计费用超限时不能批准 |
| S14 | DAG 校验 | 循环依赖、无负责人或无验收标准时不能执行 |
| S15 | 用户编辑 | 修改方案后产生新版本且必须重新校验 |

若 S01、S02、S04、S06、S07、S11、S12 或 S13 不通过，不进入正式 UI 开发。

## 标准验证场景

用户只输入需求与预算，由主模型创建“软件研发部”：

- 经理：拆解任务和验收。
- 产品经理：输出接口需求。
- 后端工程师：实现一个本地 API。
- 测试工程师：编写测试并独立验证。

任务：实现带健康检查和内存 Todo CRUD 的小型 API。要求需求、实现、测试具有明确依赖，并生成统一交付报告。

## 测试分层

- 单元测试：状态机、权限、费用计算、Adapter 映射。
- 契约测试：模型 Provider、DSH Adapter、知识工具。
- 集成测试：API + PostgreSQL + Redis + DSH。
- E2E：创建部门到交付物完成。
- 故障测试：超时、401、429、模型不可用、Runtime 重启。
- 安全测试：Prompt Injection、路径穿越、越权检索、密钥脱敏。

## MVP 验收

- 可以从 UI 创建包含 1 名经理和 1–5 名员工的部门。
- 普通用户可以只输入需求和费用上限，由主模型生成可编辑方案。
- 所有主模型方案都通过普通代码校验，不能通过提示词绕过。
- 每名员工可以选择已配置的模型。
- 配置校验能在运行前发现模型或知识库不可用。
- 计划必须人工批准。
- 用户能实时看到成员和任务状态。
- 停止、错误和重启不会造成“看似运行但实际失联”。
- 历史 Run 可查看当时的角色、模型、知识授权和成本。
- 未授权知识检索和外部写操作测试全部失败。
