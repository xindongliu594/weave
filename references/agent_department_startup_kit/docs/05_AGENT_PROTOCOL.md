# 05 Agent 与部门协议

## 员工定义

一个员工由六个维度组成：

1. Role：职责、边界和输出要求。
2. Model：Provider、模型和推理配置。
3. Knowledge：允许检索的知识空间。
4. Tools：可调用能力。
5. Permission：目录、网络和外部写权限。
6. Budget：费用、轮数、超时和并发限制。

模型不是员工身份。更换模型不应改变员工 ID、历史和权限。

## 主模型/组织规划器协议

主模型负责把 ProjectRequest 转成候选 OrganizationPlan：

- 判断任务复杂度和是否值得使用多 Agent。
- 在 `maxAgents` 内设计部门、经理与员工。
- 只能从给定 ModelCatalogSnapshot 选择模型。
- 根据模型能力、费用和任务类型进行匹配。
- 创建任务、依赖、负责人和验收标准。
- 给出费用估算、风险和降级建议。

主模型不能：

- 修改用户预算、最大并发和截止时间。
- 引用模型目录之外的模型。
- 获得或分配策略之外的工具与知识库。
- 绕过人工审批或直接启动团队。
- 接触 API Key 明文。

## 经理协议

经理必须：

- 在执行前给出成员、任务、依赖和验收标准。
- 不把任务分给无对应工具或知识权限的成员。
- 对失败任务选择重试、改派、降级或请求人工处理。
- 在汇总时标注未完成项、风险、引用和交付物。
- 不得自行扩展预算或获得新权限。

## 成员协议

成员必须：

- 仅处理当前分配任务。
- 使用当前 attempt ID 更新任务，防止过期结果覆盖。
- 发现依赖缺失时向经理报告，不自行绕过。
- 结果包含完成状态、摘要、证据、交付物和剩余风险。
- 外部写操作必须提交审批请求。

## 多模型策略

MVP 采用固定模型：Run 创建时把每位员工的 Provider/Model 固化进快照。

后续支持：

- `fixed`：始终使用指定模型。
- `fallback`：主模型失败时切换到备用模型。
- `router`：按任务能力、费用和延迟动态选择。

切换模型必须记录原因，且不能改变员工权限。

规划器与部门经理默认分离。规划器设计团队，部门经理只执行被批准的方案。小任务允许同一个模型配置承担两个角色，但必须产生两个独立的运行记录。

## 调度规则

- 默认最多 5 名成员并发。
- 只有依赖完成的任务才能进入 ready。
- 一名成员同时最多执行一个任务。
- 任务领取、改派和完成必须使用原子状态变更。
- 经理不能以“等待”为由无限轮询；等待由事件唤醒。
- 重试上限默认 2 次，超过后进入 `NEEDS_ATTENTION`。

## Runtime 映射

- Department -> Agent Team
- Manager -> Captain
- Employee -> Continuable Member Agent
- Work item -> Dependency-aware Task
- Internal message -> Durable Agent Message
- Run configuration -> Immutable Runtime Snapshot

产品后端通过 Adapter 创建和操作这些对象，不依赖自然语言提示去完成控制面动作。
